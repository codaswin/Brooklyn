| 28 | `PostgresAgentRunner` (ticket #13) already manages its own thread lock internally, for the browser path, which has no outer locker. Reusing it as ticket #21's headless-turn `RunnerLike` — now that `createTurnRunner` also takes a thread's lock itself via `access`, with the same run id it then hands to the runner — made two lock owners fight over the same row: the runner's own internal `acquire` always lost to the lock `createTurnRunner` had just taken, so every headless turn in postgres mode would have failed with "Thread already running" before the agent ever ran. Caught in self-review before it shipped, not by the delegated `code-review` (which silently reviewed the stale Windows-side OneDrive checkout instead of the WSL working copy — see the new risk row below). **First fix, shipped in ticket #21's PR, then superseded here:** a constructor option on `PostgresAgentRunner` that skipped its own lock-taking when externally locked. Dropped once ticket #22 made it unworkable — ticket #22 explicitly reuses this ONE instance for hand-off delivery too, and that instance also still has to self-lock for the browser path that calls it directly, so no single per-instance flag can be right for both callers at once. **The actual fix:** `ThreadBackend.acquire` (`postgres-thread-backend.ts`) now treats a re-acquire carrying the SAME run id as success, not a conflict — a run id is minted once per logical run and never reused, so two acquires carrying it are always the same run asking twice, never two different ones racing. This lets an external locker and the runner's own internal acquire agree they are the same holder on one shared instance, for every caller, with no flag and no special-casing. Pinned down with tests at both layers: `postgres-thread-backend.test.ts` for the bare re-acquire, `postgres-agent-runner.test.ts` and `run-turn-postgres-backend.test.ts` for the full pairing against the real runner. |

New tests (`handoff-postgres-backend.test.ts`) drive `createHandoffDelivery` against this real postgres-mode trio directly: a hop into a scratch thread, and a busy scratch thread waited for rather than failed. The "3-Bot group" Done-when item is covered structurally by the same fix (`groupConversations`' `runTurn` already went through decision #26's `createTurnRunner` fix; its hand-off-reply path goes through this one) rather than a separate new test — a genuine multi-Bot browser-level run-through is left to Aswin's Phase 4 manual checklist, same call as decision #26 made for responsibilities and proactive suggestions. |

## Risks to keep in view

| Risk | Note |
|---|---|
| LinkedIn terms restrict automation | Account can be limited or banned. Aswin's real account is at stake. Keep volumes low. Approval gates stay on. |
| Anthropic plan use | Whether using the Claude plan inside OpenBot is allowed was **not verified**. Check the current terms before relying on it. API key is the safe path. |
| Learning cost | The analyzer spends tokens against the $15 budget. Needs a cap. |
| Alpha base | OpenBot is alpha. Do not pull upstream mid-swap. |
| Free CopilotKit plan | Non-production only, 1,000 interactions per month. Only matters if we use the hosted baseline in Phase 0. |
| Browser app in new mode | Untested until Phase 4. |
| Windows Docker socket | The supervisor needs it. The native-in-WSL Docker Engine works for Postgres; the supervisor's own socket access is still untested (first exercised when `supervisor` itself runs, later phase). |
| WSL distro idle shutdown | A WSL distro instance (not just the outer VM) powers off ~15-30s after the last attached process exits, killing any running containers with it. `vmIdleTimeout=-1` in `.wslconfig` does **not** fix this (it only governs the outer VM). Workaround: keep one long-lived process attached to the distro (e.g. `wsl -d Ubuntu -- bash -lc 'tail -f /dev/null'` running in the background) for the whole duration anything inside WSL needs to stay up. Matters for every later phase that drives the stack from short-lived shell invocations. |
| Forked/background agents default to the wrong repo copy | The coding agent's session working directory is the retired Windows-side OneDrive checkout (decision #21); the agent itself always explicitly `cd`s into `~/brooklyn` in WSL2 before touching the repo, but a forked background agent (e.g. `/code-review`) has no such context and silently runs its own `git` commands against the stale OneDrive copy instead — reporting "clean, nothing to review" while real uncommitted work sits untouched in WSL. Caught during Phase 3, ticket #21. No fix yet beyond knowing to double-check; reviewing a diff via a forked agent needs the working directory pointed at `~/brooklyn` explicitly, or the review redone by hand. |
